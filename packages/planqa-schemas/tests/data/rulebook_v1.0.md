### **0. 검토 스코프**

- 검토 대상은 업로드된 기획 문서 1건이다. (PRD, 정책서, 기능 명세서, 운영 기획서 등)
- 판정 기준은 하나다 — 「이 문서만 읽은 사람이 이해하고 검증할 수 있는가」
- 카테고리는 8개, 룰은 총 41개다.

### 1. 문서 위계 정의

문서를 아래 5단위로 구분한다. 

| **위계** | **정의** | **예시 (DOC-001 홈 화면 PRD 기준)** |
| --- | --- | --- |
| 문서 | 검토 대상 문서 전체 | 「NxEF 모바일 웹 — 홈 화면 PRD」 전문 |
| 논리 단위 | 대제목 1개와 그 하위 내용 전체 | 「1. 프로덕트 목적」, 「4. 기술적 제약 사항」 |
| 문단 | 소제목 1개와 그 하위 내용 전체 | 「1-a. 문제 정의」, 「6-1. 메인 배너(캐러셀)」 |
| 문장 | 문장 1개. 표의 셀 1개, 불릿 1개도 문장으로 본다. | 「자동 슬라이드 간격: 3초」 |
| 단어 | 용어·명칭 1개 | 「PDP」, 「매입」, 「기획전 배너」 |

**위계 판정 원칙**: 지적 대상이 되는 서술들이 걸쳐 있는 범위 중 **가장 넓은 범위**를 기준으로 위계를 정한다.

- 서로 다른 대제목 2개 이상에 걸침 → **문서**
- 하나의 대제목 안, 서로 다른 소제목 2개 이상에 걸침 → **논리 단위**
- 하나의 소제목 안에서만 발생 → **문단**
- 단일 문장/셀/불릿 안에서만 발생 → **문장**

*단, 약어/명칭 정의 부재(TC-02 등)나 전제 부재(LG-01)처럼 '해당 서술이 문서 전체에 존재하는지 여부'를 스캔해야 하는 부재 확인형(Absence Check) 룰은 서술의 실제 위치와 무관하게 예외적으로 최상위인 '문서(Document)' 위계를 적용한다.

### 3. 예외조건 적용 원칙

**문서 내에 해당 항목을 가리키는 참조 표기(문서명 + 섹션)가 있으면 예외로 인정한다.**

- 문서 말미의 '관련 문서' 목록에 문서명만 나열된 것은 참조 표기로 보지 않는다. 지적 대상 항목이 있는 위치에서 그 항목을 가리켜야 한다.
- 참조 표기가 있더라도 그것이 지적 대상 항목을 가리키지 않으면 예외로 보지 않는다. (예: DOC-006 2-3의 「처리 기준은 반품/교환 정책서(DOC-005) 참고」는 반품 승인 기준에 대한 참조이므로, 같은 절의 SLA 시간 표현에 대한 예외 근거가 되지 않는다.)

## 1. 논리비약 Logic Gap

- 한줄정의: 근거와 결론, 원인과 결과, 문제와 해결책, 목표와 수행 내용 사이의 연결이 충분하지 않은 경우

| Rule ID | Rule | 예외조건 |
| --- | --- | --- |
| LG-01 | 사실·정책·의사결정·예상 효과를 확정적으로 제시하는 경우, 이를 뒷받침하는 근거나 전제를 문서 안에서 추적할 수 있어야 한다. | 업계 표준/법규처럼 문서 내 근거 제시가 불필요한 자명한 전제는 예외 |
| LG-02 | 해결방안은 하나 이상의 문제와 추적 가능한 대응 관계를 가져야 한다 | 여러 문제를 하나의 해결방안이 포괄하는 경우, 포괄 관계가 명시되면 예외 |
| LG-03 | 새로운 정책·기능은 필요성이 먼저 설명되어야 한다. | 해당 정책·기능의 필요성이 설명된 상위 문서와 섹션이 본문에 참조 표기된 경우 예외 (3장 원칙 적용) |
| LG-04 | 중간 논리 단계를 생략하여 결론으로 이어져서는 안 된다. | 독자가 이미 아는 업계 상식 수준의 단계는 생략 허용 |
| LG-05 | 성공 지표산정의 근거가 되는 전제(측정 수단, 기술 방식, 운영 방식 등)는 문서 내 다른 곳에 명시된 제약사항과 모순되어서는 안된다 | 대체 수단이 함께 명시된 경우(예: GA대신 00툴로 측정) 예외 |

## 2. 논리흐름 Logical Flow

- 한줄 정의: 내용의 전개 순서나 연결성이 자연스럽지 않아 이해가 어려운 경우

| Rule ID | Rule | 예외조건 |
| --- | --- | --- |
| LF-01 | 문단은 앞 문단과 자연스럽게 연결되어야 한다. | 섹션이 전환되는 지점(새 챕터 시작)은 예외 |
| LF-02 | 하나의 문단은 하나의 핵심 주제만 설명해야 한다. | 요약 문단은 예외 |
| LF-03 | 상위 개념은 하위 개념보다 먼저 설명되어야 한다. | 용어집/부록처럼 참조용 섹션은 예외 |
| LF-04 | 동일 주제는 가능한 연속된 위치에서 설명되어야 한다. | 문서 템플릿상 섹션이 고정되어 분리 배치가 강제되는 경우 예외 |
| LF-05 | 기능 설명은 목적→결과 , 조건→ 동작 순서를 유지해야 한다. | 표/다이어그램으로 대체 표현된 경우 예외 |

## 3. 용어 및 단어의 일관성 Terminology Consistency

- 한줄 정의: 동일한 개념을 서로 다른 용어나 표기로 사용하는 경우
- TC 내부 규칙: TC-03(기능), TC-04(UI), TC-05(행위 동사)를 우선 적용하고, 이 세 가지에 속하지 않는 '역할(사용자/관리자), 상태(활성/비활성), 정책명' 등에만 TC-01이 발동하도록 합니다.

| Rule ID | Rule | 예외조건 |
| --- | --- | --- |
| TC-01 | 동일 개념은 동일 용어를 사용해야 한다. | 인용문/외부 자료 원문 그대로 옮긴 경우 예외 |
| TC-02 | 약어는 최초 등장 시 정의해야 한다. | 해당 약어가 등재된 용어집이 본문에 참조 표기된 경우 예외 (3장 원칙 적용) |
| TC-03 | 동일 기능은 동일 명칭을 사용해야 한다. | - |
| TC-04 | 동일 UI는 동일 명칭을 사용해야 한다. | 디자인 시안 변경으로 과도기적으로 신구 명칭이 병기된 경우 예외 |
| TC-05 | 동일 행위는 동일 동사를 사용해야 한다. | - |

## 5. 모호한 표현 Ambiguous Expression

- 한줄 정의: 의미가 불명확하거나 해석이 여러 가지 가능한 표현을 사용하는 경우

| Rule ID | Rule | 예외조건 |
| --- | --- | --- |
| AE-01 | 정량화 가능한 내용은 수치로 표현해야 한다. | 해당 수치가 정의된 문서와 섹션이 본문에 참조 표기된 경우 예외 (3장 원칙 적용) |
| AE-02 | 지시어는 참조 대상이 명확해야 한다. | - |
| AE-03 | 판단 기준이 없는 표현은 구체화해야 한다. | 다음 버전에서 확정 예정임을 명시(TBD 등)한 경우 예외 |
| AE-04 | 수행 주체를 명시해야 한다. | 시스템 전역 정책처럼 주체가 자명한 경우 예외 |

## 6. 정보 누락 Missing Information

- 한줄 정의: 문서의 목적을 달성하기 위해 필요한 정보가 존재하지 않는 경우

| Rule ID | Rule | 예외조건 |
| --- | --- | --- |
| MI-01 | 기능 또는 정책의 목적이 존재해야 한다. | - |
| MI-02 | 사용자 또는 외부로부터 입력을 받는 기능은, **개발자가 임의로 판단하면 서비스 정책이 바뀌거나 예외 처리를 놓칠 수 있는 입력 조건**이 함께 정의되어야 한다. | 입력이 없는 자동 실행 기능은 예외. 업계 표준 관례를 그대로 따르는 것이 자명한 경우(예: 국내 휴대폰 번호는 010으로 시작하는 11자리)도 예외 |
| MI-03 | 처리 과정이 존재해야 한다. |  |
| MI-04 | 결과(Output)가 정의되어야 한다. | - |
| MI-05 | 예외 상황이 존재하면 예외 처리가 정의되어야 한다. | 예외 상황 자체가 발생 불가능함을 명시한 경우 예외 |
| MI-06 | 외부 시스템 연계 대상이 명시되어야 한다. | 외부 연계가 없는 기능은 해당 없음 |
| MI-07 | 시간 조건은 시작과 종료 기준이 정의되어야 한다. | 상시 실행되는 기능(종료 없음)은 예외 |
| MI-08 | 기능이 양방향 또는 대칭적 상태 변화를 전제하는 경우(ex. 상승/하강, 생성/삭제, 발급/회수 등), 반대방향의 처리도 정의되어야 한다 | 설계상 단방향만 존재함을 명시한 경우(예: 등급은 하락하지 않는 영구 등급제)는 예외 |

## 8. 상위 목표와 세부 내용의 정합성 Goal Alignment

- 한줄 정의: 상위 목표와 하위 내용(기능, 정책, 일정 등)이 일관되게 연결되지 않는 경우

| Rule ID | Rule | 예외조건 |
| --- | --- | --- |
| GA-01 | 세부 기능은 상위 목표를 지원해야 한다. | - |
| GA-02 | 정책은 요구사항과 충돌해서는 안 된다. | - |
| GA-03 | 하위 요구사항은 상위 요구사항과 일치해야 한다. | 상위 요구사항이 본문에 참조 표기되어 있고, 하위 재량 허용이 함께 명시된 경우 예외 (3장 원칙 적용) |

| GA-06 | 마일스톤에 정의된 기능은 기능 요구사항에서 정의된 기능과 일치해야 한다. |  |
| GA-07 | 기능의 우선순위는 상위 목표 기여도를 고려하여 정의해야 한다. | 법적 요구사항, 장애 대응, 기술 부채 해소 등 목표 기여도 외의 사유로 우선순위를 조정한 경우 |
