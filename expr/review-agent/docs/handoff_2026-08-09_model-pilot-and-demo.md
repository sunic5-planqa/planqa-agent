### 6. 라이브 파일럿 대신 문헌 조사로 전환

사용자가 "모델 비교 실험 때려치고 문헌으로 찾아봐"라고 지시 → 여러 각도로 웹 조사함
(전부 소스 링크 포함해서 사용자한테 제시함, 이 문서엔 결론만 요약):

- **KMMLU(한국어 벤치마크)**: Claude Sonnet 4.6 1위(85.0), Solar 2위(80.1), HyperCLOVA X
  4위(78.4), GPT-5.4 5위(78.2), EXAONE 4.0 8위(75.2, 최하위권). Gemini는 이 표에 안 나옴.
- **Function-calling 정확도**: Claude Opus >99%, GPT-4o 90-95%, Gemini 85-90% — 셀4용
  참고였는데 셀4 자체가 아래에서 드롭됨.
- **가격**: Solar Pro3가 압도적으로 저렴($0.15/$0.6 per M) — Claude Sonnet 5보다 입력
  13배, 출력 17배 쌈. Gemini 무료 티어는 $0인데 하루 250~1500건 rate limit 있음(이미
  이 프로젝트에서 겪은 문제).
- **속도(TTFT/처리량)**: Gemini Flash-Lite가 제일 빠름(TTFT 0.35초, 200~380 tok/s).
  Claude Haiku 4.5도 비슷한 급(~0.6초)이지만 가격이 Gemini/GPT의 싼 티어보다 10배 비쌈.
  GPT-5 Nano는 가격은 싼데($0.05/$0.40) 처리량은 평범(155 tok/s).
- **Recall/Precision 행동 성향** (제일 중요한 발견, 스크리닝 모델 선정 근거): 서로 다른
  3개 독립 연구(병리 분류/유해표현 탐지/티켓 분류)에서 공통적으로 **Gemini는 원래
  recall 지향(과탐지), GPT는 원래 precision 지향(보수적, 시켜도 잘 안 걸러냄)** 패턴
  확인. 스크리닝 프롬프트가 원하는 게 정확히 "의심되면 다 flag"라서 Gemini 성향과
  맞음.
- **Gemini Flash-Lite의 한국어(KMMLU) 성능은 공개 데이터가 없음** — 확인된 진짜 빈틈.
  일반 MMLU는 83-84%, "분류 작업엔 최적화, 복잡한 다단계 추론에서만 약함"이라는 정성적
  근거는 있음(스크리닝=분류 작업이라 유리한 쪽).

**결론(모두 자기편향 위험 명시하고 전달함, 사용자가 최종 결정 안 함)**:
- **스크리닝**: Gemini Flash-Lite (속도/가격/recall 성향 셋 다 부합, 이미 구축돼있음)
- **Confirm(정밀판정)**: Claude Sonnet 5 쪽으로 근거가 기움(KMMLU 1위, function-calling
  신뢰도, instruction-following) — **단 이건 내가(Claude) 나온 결론이라 자기편향
  위험이 있다고 사용자한테 반복해서 명시함.** 사용자가 최종 확정 안 함.
- **비용 추정**: Sonnet 5 기준, baseline 구조 1문서 ≈ $0.08(실측 토큰수 기반 추정).
  구조실험(5문서×~10개 구성) + 최종 20문서 전체 실행 합쳐서 **$8~23 예상, $20~30
  예산이면 안전** — 이것도 문서 1개 실측 기반 추정이라 오차 있을 수 있음.

### 7. 구조/퓨샷 계획 전면 개정 (제일 중요, 이전 handoff의 로스터를 대체함)

**이전 handoff(`handoff_2026-08-08_...md`)의 8구조+4보강 로스터는 이번 세션에서
다시 짜여졌다 — 아래 내용이 최신이다.**

배경: 사용자가 지도 아티팩트를 다시 보다가 "왜 스크리닝에도 룰 전문을 다 주냐,
카테고리만 줘야 하는 거 아니냐"는 질문을 함 → 이게 "세분화(카테고리/룰 단위)"와
"룰 정보 전달 방식(전문 명시/퓨샷)"이 사실 같은 축의 문제라는 걸 깨닫는 계기가 됨.
사용자가 직접 아래처럼 재정리함:

**새 실험 순서(사용자가 직접 지정)**:
1. 판정 단계 수 (제안0 vs 제안5) — 제일 먼저 확정
2. 청킹 방식 (위계형 vs 문단형) — 그 다음
3+4. 세분화 × 퓨샷 방식 — **같이 묶어서** 실험(순서 안 매김)

**①②는 이름만 새로 붙임, 내용은 이전 handoff와 동일**:
- 직접판정형(구 제안0) vs 2단계형(구 제안5, baseline)
- 위계형(구 방안2) vs 문단형(구 방안1, GA는 예외적으로 문서 전체 1회)

**③+④는 완전히 새로 짠 6조합 매트릭스** (2×3):

| | 룰전부명시 | 퓨샷만 | 동적퓨샷 |
|---|---|---|---|
| **콜통합**(카테고리 전부 1콜) | 콜통합×룰전부 | 콜통합×퓨샷만 | 콜통합×동적퓨샷 |
| **콜분리**(카테고리마다 1콜) | **콜분리×룰전부 = 이미 만든 셀3** | 콜분리×퓨샷만 | 콜분리×동적퓨샷 |

→ 6개 중 1개 이미 구현됨, 5개만 새로 만들면 됨.

**드롭된 것— 셀3R(룰분리형)/셀4(룰분리+tool-calling)**: 재검토 결과 위 6조합
매트릭스로 사실상 다 커버됨(룰 단위 세분화는 "퓨샷" 축의 극단적 형태) + 셀4의
tool-calling/건너뛰기 아이디어는 원래 "룰 수십 개를 낱개로 호출하면 너무 비싸다"는
문제를 풀려던 건데, 세분화를 카테고리 단위(최대 8개)까지만 하기로 하면서 그 비용
문제 자체가 사라짐 → 실익 없어서 드롭. **이미 만든 `cell3r.py`는 안 지우고 보류.**

**중요 제약 발견 — eval-agent 코드 직접 읽고 확인함**: `matcher.py`가 golden/predicted를
`(doc_id, category)`로 버킷 나누는데 **category를 predicted의 rule_id에서 역산**해서
구함. `verifier.py`는 golden/predicted rule_id가 **완전히 같은지**로 정오답 가림(유사도
아님). → **"퓨샷만"/"동적퓨샷" 조합도 최종 출력엔 반드시 구체적인 rule_id를 하나
찍어서 내야 함** — eval-agent는 고정이라 이 요구사항을 피할 방법이 없음. "카테고리만
말해도 됨"은 내부 판단 과정 얘기지, 최종 스키마 얘기가 아님.
