## 이번 세션에서 정리된 것 — 순서대로

### 1. 구조 실험의 대전제 (가장 중요, 절대 어기면 안 됨)

**이미 만든 구조의 코드는 절대 고치지 않는다. 항상 새 모듈을 추가한다.** (사용자가 명시적으로
정정: "있는 구조 고치면 안되고, 추가해야돼")

- 이유: 이건 여러 파이프라인 구조를 서로 비교하는 **ablation 연구**다 (어느 회사 모델이
  더 좋다는 리더보드가 아니라, **우리 내부 통제 변수**(구조/퓨샷/모델)가 각각 결과에 얼마나
  영향을 미치는지 격리해서 보는 것). 이미 측정 끝난 구조의 공용 코드를 나중에 고치면 그
  구조의 이미 나온 숫자가 조용히 무효화된다.
- **공용 유틸은 재사용 OK** (사용자 확인: "공통 유틸은 그대로 써도 돼") — `document.py`
  (청킹), `schema.py`, `rulebook.py`(파싱), `dedupe.py`, `instrumentation.py`, `llm/*`
  (클라이언트+계측)은 어느 구조를 쓰든 똑같아야 공정한 비교가 되므로 계속 공용으로 쓴다.
- **손대면 안 되는 것**: `pipeline.py`(baseline 구조 로직 자체), `models/gemini_lite/*`
  (baseline 프롬프트). 새 구조는 `structures/<name>.py` 같은 새 파일로 만들고, 필요하면
  gemini_lite 프롬프트를 참고/복사하되 원본은 안 건드림.
- 새 구조를 만들기 전엔 **항상 먼저 설계를 대화로 논의하고 합의한 뒤에 코드를 짠다** —
  다음 세션이 바로 코드부터 짜지 말 것.

이 두 원칙(추가 전용, 코딩 전 설계 합의)을 `feedback_additive_structures_only.md`
메모리에 저장해둠 — 이 프로젝트 관련 세션이면 자동으로 로드되어야 함.

### 3. 구조 로스터 — 최종 합의된 8개 + 조건부 규칙

`docs/review_agent_architecture.md`에는 아직 반영 안 했음 — 이 handoff 문서와 아래 아티팩트가
현재 유일한 최신 기록.

**확정 5개 (무조건 다 만듦)**

| 이름 | 정의 |
|---|---|
| 제안0 | **신규 제안**. 위계 청킹 그대로, 스크리닝→정밀판정 2단계를 없애고 위계당 1콜로 바로 최종 판정까지 끝냄. "2단계 구조 자체가 값어치를 하는가"를 보는 바닥값(floor). |
| 제안5 | **이미 완성됨** (`pipeline.py` + `models/gemini_lite/*`). baseline. 위계 청킹, 위계당 배정된 카테고리 전체를 한 콜로 스크리닝→정밀판정. 손대지 않음. |
| 셀3 (방안2×1안) | 위계 청킹 그대로, 위계 안에서 **카테고리별로 독립 호출**을 병렬 실행. **진짜 tool-calling 없음** — 위계별 카테고리 배정이 룰북 §2로 이미 결정론적이라 모델이 "선택"할 게 없어서, 실제 function-calling 대신 그냥 병렬 API 호출로 충분하다고 판단함(사용자 동의). |
| 셀3R | **신규 제안, 셀3과 셀4 사이의 빠진 칸을 메우려고 추가**. 셀3과 청킹/세분도는 같은데 카테고리 단위가 아니라 **룰 단위**까지 병렬로 쪼갬, tool-calling은 여전히 없음. 이게 없으면 셀3→셀4에서 "세분도"와 "tool-calling 도입"이 동시에 바뀌어서 어느 쪽 효과인지 못 가름 — 셀3R을 끼워 넣어서 순수 분리함. |
| 셀4 (방안2×2안) | 셀3R과 청킹/세분도(룰 단위)는 같고, **모델에게 룰별로 tool-calling으로 건너뛸 자유를 줌**. 스킵 허용 여부 논의: 카테고리 단계에서 이미 recall 우선으로 걸러졌으니, 룰 단위에서 스킵 허용이 상대적으로 안전하다고 판단 — 스킵 허용하는 쪽으로 구현 권장(아직 최종 확정은 아님, 셀4 만들 때 다시 확인). tool-calling 메서드는 `llm/gemini.py`에 아직 없음 — 셀4 시작 시점에 새로 추가하기로 함(공통 선행 작업에서 지금 당장은 미룸). |

**조건부 3개 (위 5개 결과 보고 범위 결정 — 미리 정하지 않음)**

| 이름 | 정의 |
|---|---|
| 셀1 (방안1×1안) | 문단 청킹(위계 4단계 없이 문단 하나로만 자름) + 카테고리별 병렬. **GA 예외**: "상위 목표와의 정합성"(GA) 카테고리는 문단 하나만 봐서는 비교할 "상위 목표"가 그 안에 없어서 판단 불가 — 룰북 §2 자체도 GA를 Paragraph 위계에서 제외하고 있음(문서/논리단위에서만 체크). 그래서 셀1/셀1R/셀2는 나머지 7개 카테고리만 문단 단위로 병렬 처리하고, **GA 하나만 문서 전체를 놓고 딱 한 번 별도 호출**로 확인. |
| 셀1R | 셀1과 같되 룰 단위까지 세분화. GA 예외 동일 적용. |
| 셀2 (방안1×2안) | 셀1R과 같되 룰 단위 tool-calling 추가. GA 예외 동일 적용. |

**조건부 규칙(중요, 잊지 말 것)**: 위 확정 5개(제안0, 제안5, 셀3, 셀3R, 셀4)를 먼저 다
만들고 결과를 본다. 결과가 한쪽으로 깔끔하게 기울면(예: "룰 단위로 갈수록, tool-calling
넣을수록 계속 좋아지더라") 문단 쪽(셀1/1R/2)은 **그 중 제일 효과 컸던 지점 딱 하나만**
만들어서 "문단으로 나눠도 비슷한가?" 확인. 결과가 애매하거나 중간에 역전 조짐이 있으면
더 만든다. **미리 "문단은 몇 개 만들지" 숫자를 정해두지 않는다** — 위쪽 3개(셀3·셀3R·셀4)
결과를 실제로 보고 나서 그때 판단.

이렇게 하는 이유(정리): 카테고리 단계에서만 위계/문단 비교하고 미리 청킹 방식을 확정해버리면,
룰 단위+tool-calling까지 내려갔을 때 역전이 생겨도 놓친다 — 하필 역전 가능성이 제일 큰
지점(룰+tool-calling)을 안 보고 넘어가는 셈이라 위험. 반대로 6개를 무조건 다 만드는 것보다는
확실히 싸다. "0 vs 5"도 같은 논리로 처리했음: 제안0/제안5는 몇 단계로 나눌지의 축이고
셀3~셀2는 어떻게 쪼개서/나눠서 묻는지의 축이라 서로 다른 질문 — 0 vs 5는 위계 청킹 기준으로
딱 한 번만 비교해서 정하고, 그 결과(1단계냐 2단계냐)를 위/아래 줄 둘 다에 그대로 적용하기로
함(이것도 위험을 감수하는 선택 — 청킹에 따라 결과가 다를 수도 있는데 그건 8개 다 만든 뒤
이상한 조짐 보이면 그때 추가 확인하기로).

**선택 4개 (8개 다 만들고 최선 구조 고른 뒤, 그 구조 하나에 필요한 것만 하나씩 켜서 비교)**

| 이름 | 정의 |
|---|---|
| 제안6 | Generator-Critic. confirm 이후 재검토 단계 하나 추가. 새 구조 아님, 기존 구조 위에 얹는 보강. |
| 제안7 | Chain-of-Verification. 판정을 하위질문 체인으로 쪼개서 검증. 역시 얹는 보강. |
| 제안8 | **신규 제안**. confirm 호출을 위계당 1회가 아니라 문서당 1회로 배치 축소 — 호출 수 줄이는 대신 프롬프트 커지는 트레이드오프 확인. |

### 5. 모델 선택 — 아직 미결정, 다음 세션이 이어서 결정해야 함

이 부분이 **이번 세션의 마지막 화두였고 결론이 안 났음**. 흐름:

1. 처음엔 "기존 Gemini 클라이언트 재사용 + 유료 티어로 업그레이드"를 제안 (엔지니어링
   비용 0). `llm/gemini.py`의 하드코딩된 기본 모델 `"gemini-2.5-flash"`가 **2026년 10월
   16일 단종 예정**이라는 걸 발견 — 이건 지금 코드베이스의 실제 버그이자 시한폭탄이니
   구조 실험과 별개로 언젠가 고쳐야 함(아직 안 고침).
2. 사용자가 "제미나이 안 써도 돼, 전체적으로 검토해봐"라고 확장 요청 → Claude/GPT/Gemini
   비교 조사 → 처음엔 Claude Sonnet 5를 한국어 벤치마크(KMMLU) 근거로 추천.
3. 사용자가 날카롭게 지적: "네가 클로드니까 그거 선택하지 말고" — 자기 편향 위험 있는
   판단이었음을 인정하고 재검토. KMMLU는 지식 벤치마크지 생성 품질 벤치마크가 아니라는
   것도 스스로 지적함. 한 번은 "브랜드 상관없이 아무 안정적인 모델이나 고정하면 된다"는
   방향으로 후퇴했었음(Gemini로 회귀).
4. 사용자가 다시 정정: "상대적 차이는 뭘로든 잴 수 있지만, 실제로 룰 위반을 잘 잡고
   한국어 수정 제안을 잘 쓰는 모델이어야 나중에 진짜 서비스에 쓴다고 가정했을 때 합리적"
   — 이게 맞는 지적. 모델 브랜드가 결과에 안 중요하다는 이전 결론은 틀렸음(3번 항목의
   "이걸 물어보는 이유"와 직결).
5. **최종 합의된 해법**: 벤치마크나 내 판단으로 고르지 말고, **실제로 이 태스크(baseline
   구조 제안5 하나만 재사용)로 후보 모델 몇 개를 작은 파일럿으로 직접 재본다.**
   - 이미 있는 문서 2~3개(예: DOC-003/004/005, 골든 데이터셋 있는 것들)만 각 후보 모델로
     제안5(baseline) 구조를 돌림 — **전체 8구조 인프라는 안 건드리고, 후보 모델별
     클라이언트/프로필만 새로 만들면 됨** (예: `models/<candidate>/`, `llm/<candidate>.py`
     — 이것도 "새 구조를 추가하는 게 아니라 baseline 구조에 새 모델을 꽂는 것"이라 2번의
     "추가 전용" 원칙과 배치되지 않음, `models/__init__.py`의 `PROFILES` 레지스트리 패턴

### 6. eval-agent 확인 결과 (참고용, 이미 끝난 조사)

`feature/eval-agent` 브랜치(읽기 전용, 절대 수정 금지)를 확인해서 사람-vs-에이전트 교차검증
경로가 실제로 있고 끝까지 연결돼 있음을 확인함:

- **2-1 confidence gate** (`planqa-eval gate`): 자동 매칭/채점 로직 자체가 믿을 만한지
  검증하는 게이트 — review-agent와 직접 관련 없음, 2-2 돌리기 전에 통과해야 하는 선행 조건.
- **2-2 사람 베이스라인 비교** (`planqa-eval evaluate` 안에서 자동 실행): review-agent의
  `review.json`과 xlsx의 `Review1~6` 시트(사람 리뷰어별)를 **완전히 같은 파이프라인**으로
  돌려서 recall/precision을 1:1 비교. `report.json`의 `baseline_comparison` 필드,
  `report.md`의 "## Vs. Human Baseline" 섹션까지 실제로 렌더링됨 — 끝까지 연결된
  기능임을 코드로 확인함.
- review-agent의 `diff_report.py`가 `issue_id`를 `REV-{doc_id}-{순번}` 형식으로 자동
  채워주고 있어서, 이 비교 기능이 필요로 하는 `issue_id` 요구사항과 이미 호환됨 — 추가
  작업 불필요.
- 이 조사는 순수 읽기 전용 확인이었고, 지금 당장 실행하라는 지시는 없었음(나중에 실제
  8구조 다 만들고 나서, 각 구조의 review.json을 eval-agent에 넘겨 정확도 확인하는 흐름의
  일부로 쓰일 예정).
