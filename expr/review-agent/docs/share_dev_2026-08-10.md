# [공유] review-agent 구조 실험 중 발견한 버그/변경사항 (개발팀용, 2026-08-10)

review-agent(기획서 검토 에이전트)의 구조 ablation 실험을 진행하면서, 실험과 무관하게 실제 코드에 영향을 주는 버그 몇 개와 재사용 가능한 개선사항을 발견/적용했습니다. `feature/review-agent` 브랜치에 있고 아직 커밋 전이라, 다른 브랜치/서비스에 비슷한 패턴이 있다면 참고하시면 좋을 것 같습니다.

## 1. 병렬 디스패치 구조의 비용 계측 버그 (실사용 영향 있음)

카테고리별로 `ThreadPoolExecutor`를 써서 LLM 콜을 병렬로 보내는 구조(`cell3`, `direct_verdict` 등)에서, 여러 스레드가 같은 LLM 클라이언트 인스턴스를 공유하다 보니 "호출 전후 usage 리스트 길이 차이"로 비용을 태깅하는 방식이 스레드 레이스에 걸렸습니다.

- 실제 API 호출은 정상이었지만, 계측(호출 수/토큰/시간 통계)이 최대 3배까지 부풀려졌습니다.
- 원인: `record_call()`이 공유 클라이언트 객체의 `usage` 리스트를 before/after로 diff하는데, 동시에 여러 스레드가 같은 리스트에 append하면 서로의 호출을 중복으로 잡아먹습니다.
- 수정: 카테고리마다 클라이언트를 얕은 복사(`copy.copy`)해서 격리된 `usage` 리스트를 쓰게 하고, 끝나면 원본에 합치는 방식(`instrumentation.py`의 `isolate_client`/`merge_usage`)으로 해결. 레이스를 실제로 재현하는 테스트도 추가했습니다.
- **다른 곳에서도 스레드 풀로 LLM 클라이언트를 공유해서 쓰는 코드가 있다면 같은 버그가 있을 수 있습니다.**

## 2. LLM이 깨진 JSON을 낼 때 결과가 통째로 유실되던 버그

모델이 "JSON만 응답하라"고 지시받아도, 가끔 이스케이프 안 된 백슬래시(윈도우 경로, 정규식 조각 등)나 트레일링 콤마를 응답에 넣어서 `json.loads`가 실패하는 경우가 있었습니다. 이 경우 그 호출 전체의 결과가 조용히 사라졌습니다(API 과금은 됐는데 결과가 없음).

- 수정: `llm/base.py`의 `parse_json_response`에 복구 폴백을 추가 — 1차 strict parse 실패 시 (1) 잘못된 `\uXXXX` 이스케이프, (2) 그 외 유효하지 않은 백슬래시, (3) 트레일링 콤마를 정규식으로 복구해서 재시도. 복구도 실패하면 원래 예외를 그대로 냅니다(진짜 깨진 응답을 조용히 삼키지 않음).
- 모든 LLM 백엔드가 공유하는 진입점이라 한 곳만 고치면 전체(Gemini/Anthropic/Ollama/Gateway)에 적용됩니다.

## 3. Gemini 기본 모델이 죽어있던 버그

`llm/gemini.py`의 `DEFAULT_MODEL = "gemini-2.5-flash"`가 "신규 사용자에게 더 이상 제공 안 됨"(404)으로 완전히 막혀 있었습니다. `gemini-flash-lite-latest`로 교체했습니다. 같은 날 팀원분이 `eval-service`에서 독립적으로 같은 값으로 고친 걸 확인해서 교차 검증됐습니다 — 다만 `tools/eval-agent`(모노레포의 CI용 사본)에는 아직 이 픽스가 안 들어가 있을 겁니다.

## 4. Anthropic 프롬프트 캐싱 도입 (재사용 가능한 패턴)

같은 문서에 대해 카테고리마다 별도 LLM 콜을 날리는 구조는, 매 콜마다 같은 문서 본문을 다시 전송합니다. `llm/base.py`의 `complete_json`에 `cache_prefix` 파라미터를 추가하고, `llm/anthropic.py`에서 실제로 `cache_control: {"type": "ephemeral"}` 블록을 써서 (a) 시스템 프롬프트(구조마다 고정 텍스트라 항상 캐시), (b) 카테고리 콜들이 공유하는 문서 본문(주어졌을 때만 캐시)을 캐시 브레이크포인트로 마킹했습니다.

- 다른 백엔드(Gemini/Ollama/Gateway)는 `cache_prefix`를 그냥 이어붙이기만 해서 하위호환 유지, 기능 차이 없음.
- Claude Sonnet 등 캐싱 지원 모델로 같은 문서 내 반복 호출이 많은 구조라면 바로 재사용 가능한 패턴입니다.

## 5. 그 외

- `ThreadPoolExecutor`의 `max_workers`를 고정값 대신 "이번 배치의 실제 작업 수"로 동적으로 잡도록 바꾼 사례가 있습니다(`paragraph_verdict.py`/`category_fewshot.py`) — 작업 수가 max_workers보다 적을 때 불필요하게 큰 풀을 만들 필요는 없지만, 반대로 작업 수가 많은데 max_workers가 낮으면 배치로 나눠 돌아서 wall time이 늘어납니다. 작업 수를 안다면 그만큼 잡는 게 낫습니다.
- 위계(계층) 기반 이슈 리포팅 구조에서, "지금 처리 중인 청크의 계층"과 "실제 이슈가 영향을 미치는 범위"가 다를 수 있다는 걸 모델이 스스로 판단해서 알려줄 수 있게 스키마에 필드를 추가한 사례가 있습니다(`document.py`의 `resolve_reported_level` — 항상 승격만 허용, 축소는 무시). 비슷하게 "모델이 준 청크보다 넓은 범위에 걸친 판단"이 필요한 다른 기능에도 참고할 만한 패턴입니다.
