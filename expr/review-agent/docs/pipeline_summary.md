# 검토 에이전트(review-agent) 파이프라인 & 산출물 메타데이터 요약

> 팀 공유용 정리 문서. 기술적으로 더 자세한 내용은 `docs/review_agent_architecture.md` 참고.

## 1. 지금 구현한 검토 방식

### 한 줄 요약
**"스크리닝(넓게, 싸게) → 정밀판정(좁게, 정확하게)" 2단계**를, **문서 위계(문서/논리단위/문단/문장) 4단계**로 나눠서 반복 수행한다. 룰북은 카테고리별로 위계에 배정은 해두지만, 실제로 모델에게 물어볼 때는 **룰마다 별도 도구(tool)나 에이전트로 나누지 않고, 해당 위계에 배정된 룰들의 텍스트를 그냥 하나의 프롬프트 문자열 안에 통째로 나열**해서 한 번의 호출로 보낸다.

### 왜 이렇게 했는지
- 룰북 §2("카테고리별 검토 위계")가 이미 "이 위계에서는 이 카테고리들만 본다"를 정적으로 정해준다. 즉 "다음에 뭘 검토해야 하지?"를 모델이 스스로 판단할 필요가 없는 문제라, 모델이 알아서 룰을 골라잡게(tool-calling) 하지 않고 정해진 룰 목록을 텍스트로 통째로 넘기는 쪽이 더 저렴하고 결과가 일관적이다.
- 위계별로 스크리닝 1번 + (후보가 있으면) 정밀판정 1번, 총 최대 9번의 호출로 문서 하나를 끝낸다 — 호출 수가 고정적이라 비용/시간 예측이 쉽다.

### 구체적 흐름 (문서 1건 기준)

| 단계 | 하는 일 | 사용 모델 |
|---|---|---|
| 1. Global Context 추출 | 문서 전체를 1번 읽고 목적/핵심 정책을 압축 요약 — 이후 모든 프롬프트 앞에 붙여서 매번 전체 문서를 다시 첨부 안 해도 되게 함 | 정밀판정용 모델 |
| 2. 위계 분할 | 마크다운 헤딩 구조로 문서/논리단위/문단/문장 4단계로 자동 분할 (순수 코드, LLM 사용 안 함) | - |
| 3. 위계별 스크리닝 | 위계마다 배정된 룰들의 텍스트 + 그 위계의 청크 전체를 프롬프트에 넣어서, "의심되는 부분"을 넓게(recall 우선) 나열하게 함 | 저비용 모델 |
| 4. 위계별 정밀판정 | 스크리닝에서 나온 후보마다 룰 전문 + 예외조건 + 원문 전체를 다시 보내서, 진짜 위반인지 엄격하게 재확인하고 원문 인용/근거/개선안을 받음 | 고비용 모델 |
| 5. 예외조건 확정 | 룰북 §3의 "참조 표기가 있으면 예외" 대상 룰(현재 LG-03/TC-02/AE-01/GA-03)은 모델의 자기 판단을 안 믿고, 코드로 짠 결정론적 로직으로 최종 확정 | - (코드) |
| 6. 중복 제거 | 여러 위계에서 같은 문제가 겹쳐 지적된 경우 가장 구체적인 위계의 것만 남김 | - (코드) |
| 7. 리포트 생성 | `review.json`(구조화 데이터) + `review.md`(원문→제안을 diff 형태로 렌더링) 출력 | - (코드) |

### 지금 안 하고 있는 것 (참고)
- 룰 카테고리를 모델이 스스로 선택하는 tool-calling 구조 아님
- 여러 에이전트가 병렬로 판단을 나눠 갖는 멀티에이전트 구조 아님
- 위계 4단계가 실제로는 순차 실행(sequential) — "병렬"이라 부르기엔 아직 아님

## 2. 실행 결과(`review.json`)에 남는 메타데이터 설명

매 실행마다 `stats` 항목에 아래 값들이 자동으로 기록된다. 여러 모델/프롬프트 조합을 실험할 때 "이 결과가 어떤 조건으로 나온 건지"를 나중에도 정확히 추적하기 위한 것.

| 필드 | 의미 |
|---|---|
| `profile` | 어떤 프롬프트/로직 전략을 썼는지 (예: `gemini_lite`) — 나중에 여러 파이프라인 구조를 실험하면 여기 값으로 구분됨 |
| `backend` | 어떤 LLM 제공사를 썼는지 (`gemini` / `ollama`) |
| `screen_model` | 스크리닝(1단계)에 실제로 쓴 모델 이름 |
| `verify_model` | 정밀판정(2단계)에 실제로 쓴 모델 이름 |
| `rulebook_hash` | 이 실행에 사용된 룰북 파일의 콘텐츠 해시(12자리). 룰북 파일 안의 "V1.0" 버전 표기는 룰 내용이 바뀌어도 안 바뀌기 때문에, 정확히 어느 시점 룰북으로 나온 결과인지 이 해시로 추적한다(레포의 `git log` 기록과 대조하면 정확한 룰북 상태를 다시 찾을 수 있음) |
| `total_wall_seconds` | 문서 1건을 검토하는 데 걸린 **총 실제 시간**(초). 재시도 대기 시간까지 포함 — 무료 티어라 자주 막히는 모델은 그것도 "실제로 느리다"는 뜻이라 일부러 안 뺐음 |
| `screen.call_count` | 스크리닝 단계가 호출된 횟수 (위계 4개 = 보통 4) |
| `screen.elapsed_seconds` | 스크리닝 호출들에 실제로 걸린 시간의 합 |
| `screen.total_tokens` | 스크리닝 호출들에서 쓴 입력+출력 토큰 합 |
| `confirm.call_count` | 정밀판정 단계가 호출된 횟수 (Global Context 추출 1회 + 후보가 나온 위계 수) |
| `confirm.elapsed_seconds` | 정밀판정 호출들에 실제로 걸린 시간의 합 |
| `confirm.total_tokens` | 정밀판정 호출들에서 쓴 입력+출력 토큰 합 |

**용도**: 이 필드들을 모아두면, 나중에 "프롬프트/파이프라인 구조 A vs B vs C"를 비교할 때 시간·토큰(비용) 축은 이 메타데이터로, 정확도 축은 평가 에이전트(`eval-agent/`)로 각각 측정해서 종합적으로 어떤 조합이 제일 나은지 판단할 수 있다.

### 그 외 산출물 필드
- `issues`: 실제 지적 사항 목록 (룰ID, 위치, 원문 인용, 문제 설명, 근거, 개선안)
- `tier_errors`: 일부 위계에서 모델 응답 파싱이 실패했을 때, 그 사실을 숨기지 않고 명시적으로 남기는 필드 (나머지 위계 결과는 정상적으로 살아있음)
