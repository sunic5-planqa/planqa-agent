# 검토 에이전트(2차 데모) 구현 방식 설명

> 이 문서는 기획팀 발표자료 준비를 위해, 2차 데모에서 실제로 서비스되는 검토 에이전트가
> 어떻게 동작하는지 정확하게 설명하기 위해 작성됐다. 팀에 돌던 기존 아키텍처 다이어그램
> (문서 전체 → 대제목 → 소제목 → 문장, 4단계로 좁혀가며 카테고리를 검토하는 그림)은
> **실제 구현과 다르다** — 그건 룰북을 처음 설계할 때 세운 4단계 구상이고, 실제로
> 구현·배포된 구조는 이 문서에서 설명하는 더 단순한 2단계 구조다. 발표자료에는 이
> 문서의 내용을 반영해야 한다.

## 1. 한눈에 보는 파이프라인

### 1-1. 설계를 관통하는 3가지 원칙

세부 내용(3~6절)에 들어가기 전에, 전체 구조를 왜 이렇게 짰는지 먼저 요약한다.

1. **"넓게 훑고, 좁게 확정한다"** — 값싸고 빠른 모델이 넓게 의심 후보를 모으고,
   비싸고 정확한 모델이 그중 진짜만 골라낸다. 한 모델에게 처음부터 끝까지 다 시키지
   않는다. (→ 4절)
2. **"비교가 필요한 룰은 비교할 수 있는 시야를 준다"** — 대부분의 룰은 문단 하나만
   봐도 판단 가능하지만, "이 문장과 저 문장이 서로 모순되는가" 같은 룰은 애초에 두
   부분을 동시에 봐야 판단할 수 있다. 그런 룰만 예외적으로 문서 전체를 보여준다. (→ 3절)
3. **"모델이 실제로 판단한 범위를 있는 그대로 존중한다"** — 문단 하나를 검토하라고
   시켰어도, 모델이 "이건 사실 더 큰 범위의 문제"라고 판단하면 그 판단을 그대로
   인정해서 보고한다. 검토 단위와 보고 단위를 억지로 일치시키지 않는다. (→ 6절)

### 1-2. 문서 한 개가 실제로 처리되는 과정 (예시로 따라가 보기)

`DOC-003_상품상세페이지_PRD.md` 라는 기획서 한 개가 들어왔다고 하면, 아래 순서로
처리된다.

**1단계 — 문서 전체 요약 추출 (1회, 고성능 모델)**
문서 전체를 한 번 읽고 "이 문서의 목적/핵심 정책/KPI가 뭔지" 짧게 요약한다. 이 요약은
이후 모든 검토 호출에 공통으로 딸려가서, 각 호출이 문서 전체를 매번 다시 읽지 않아도
전체 맥락(이 문서가 뭘 하려는 문서인지)을 알고 판단할 수 있게 해준다.

**2단계 — 검토 단위로 자르기**
문서를 카테고리에 따라 "문단" 또는 "문서 전체" 단위로 나눈다(정확한 기준은 3절).
`DOC-003`은 문단이 여러 개인 일반 기획서라 대부분 문단 단위로 쪼개지고, GA/LG/LF
카테고리(와 LG-01/TC-02)만 문서 전체 그대로 유지된다.

**3단계 — 1차 스크리닝 (문단 pass·문서 pass, 각각 1콜씩, 저비용 모델)**
문단 전체를 한 번의 호출에 다 넣고(문서 하나당 문단 개수와 무관하게 스크리닝은 pass당
딱 1콜), "각 문단이 어떤 룰을 위반했을 가능성이 있는지" 넓게 훑어서 후보 목록을
뽑는다. 이 단계는 의도적으로 관대하다 — 애매하면 일단 후보에 넣는다. 문서 pass도
동시에(병렬로) 같은 방식으로 진행된다.

**4단계 — 2차 정밀판정 (후보 개수만큼, 고성능 모델)**
스크리닝이 뽑은 후보 하나하나를 정밀 모델이 다시 검토해서, 진짜 위반인지
(`violated: true/false`) 최종 판정한다. 이 단계에서 대부분의 후보가 "위반 아님"으로
걸러진다. 실제로 위반으로 확정되면, 왜 위반인지·어떻게 고치면 되는지·어느 범위의
문제인지(6절)까지 함께 만들어낸다.

**5단계 — 결과 취합**
문단 pass와 문서 pass에서 나온 위반 목록을 합치고, 같은 문제를 중복으로 지적한 게
있으면 하나로 정리해서 최종 결과로 낸다.

한 문서를 검토하는 데 실제로 걸리는 LLM 호출 수는 문서 크기에 따라 다르지만, 이
구조(`bundled_screen_hybrid`)는 실측 기준 문서당 평균 4~5콜 정도로 끝난다(요약 추출
1콜 + 문단/문서 pass 스크리닝 각 1콜 + 후보 개수만큼의 정밀판정 콜) — 문단마다,
룰 카테고리마다 따로따로 호출하는 방식보다 훨씬 적은 호출로 끝난다 — 이것도 "왜 이
구조를 택했는지"의 한 축이다(7절에서 비용까지 같이 정리).

2단계(스크리닝 → 정밀판정)로 나눈 이유는 4절에서, 청킹 기준은 3절에서 자세히 설명한다.

## 2. 무엇을 검토하는가 — 룰북 8개 카테고리

기획서를 40여 개의 세부 룰로 검토하는데, 이 룰들은 8개 카테고리로 묶여 있다.

| 카테고리 코드 | 이름 | 한 줄 정의 |
| --- | --- | --- |
| LG | 논리비약 (Logic Gap) | 근거-결론, 원인-결과, 문제-해결책 사이의 연결이 충분하지 않은 경우 |
| LF | 논리흐름 (Logical Flow) | 내용의 전개 순서·연결성이 자연스럽지 않아 이해가 어려운 경우 |
| TC | 용어 일관성 (Terminology Consistency) | 동일 개념을 서로 다른 용어·표기로 쓰는 경우 |
| TM | 용어 오용 (Terminology Misuse) | 용어를 의미와 다르게, 또는 부적절하게 쓰는 경우 |
| AE | 모호한 표현 (Ambiguous Expression) | 의미가 불명확하거나 여러 해석이 가능한 표현 |
| MI | 정보 누락 (Missing Information) | 목적 달성에 필요한 정보(주체, 처리 과정, 결과, 예외처리 등)가 빠진 경우 |
| RD | 불필요한 중복 (Redundancy) | 동일하거나 유사한 내용을 반복 서술하는 경우 |
| GA | 상위 목표 정합성 (Goal Alignment) | 상위 목표와 하위 내용(기능/정책/일정)이 어긋나는 경우 |

## 3. 문서를 자르는 단위 (청킹)

에이전트는 문서 전체를 한 번에 보지 않고, 검토하기 좋은 작은 단위로 잘라서 하나씩
넣는다. 지금 구현은 **딱 2가지 단위**를 쓴다 — 어떤 카테고리인지에 따라 둘 중 하나로
배정된다.

| 검토 단위 | 대상 카테고리/룰 | 이유 |
| --- | --- | --- |
| **문서 전체** (1개 청크) | GA(상위 목표 정합성), LG(논리비약), LF(논리흐름) 카테고리 전부, 그리고 개별 룰로 LG-01("근거가 문서 안에 있어야 한다")과 TC-02("약어는 최초 등장 시 정의") | 이 룰들은 "서로 다른 두 위치를 비교"하거나 "문서 전체 어딘가에 있는지 확인"해야 판단 가능 — 한 문단만 봐서는 답을 낼 수 없다 |
| **문단** (문서 안 문단 개수만큼) | 나머지 전부(TC의 다른 룰, TM, AE, MI, RD 등) | 한 문단 안에서 판단 가능한, 국소적인 문제들 |

**왜 이렇게 나눴나**: GA/LG/LF 같은 카테고리는 정의상 "서로 다른 두 문장/섹션이 충돌
하는가"를 판단하는 룰이다. 예를 들어 "1장에서 밝힌 KPI"와 "4장에서 정의한 기술 제약"이
서로 모순되는지 확인하려면, 그 두 부분을 동시에 볼 수 있어야 한다. 처음엔 이런 룰도
문단 단위로 쪼개서 검토했는데, 실제로 **DOC-001 문서의 KPI-기술제약 충돌, DOC-012
문서의 KPI-마일스톤 충돌을 완전히 놓치는 사례**가 나왔다 — 문단 하나만 보는 시야로는
애초에 비교 대상을 만날 기회가 없었기 때문이다. 그래서 이 카테고리들만 문서 전체를
한 번에 보여주도록 바꿨다.

## 4. 왜 2단계(스크리닝 → 정밀판정)인가

한 번에 정밀한 모델이 전체를 다 판정하게 하는 방식(1단계)도 실험해봤다. 결과:

- 정밀한 모델(Claude Sonnet)을 스크리닝 없이 혼자 쓰면, 걸러지지 않은 채 지나치게
  많은 후보를 "위반"으로 판정해버렸다(실험에서 판정 애매/보류 건수가 90건 이상까지
  치솟음 — 저렴한 모델이 먼저 후보를 추리는 2단계 구조에서는 20건대로 줄었다).
- 저렴한 모델 혼자 2단계를 다 하면(둘 다 저비용 모델) 반대로 추론력이 부족해서 실제
  위반을 놓치는 경우가 많았다.

그래서 **"저비용 모델이 넓게 후보를 훑고(recall 우선) → 고성능 모델이 그 후보만
정밀하게 재판정(precision 우선)"** 하는 2단계 구조로 확정했다. 지금 데모2가 실제로
쓰는 모델 조합:

- 1차 스크리닝: **Gemini flash-lite** (저비용)
- 2차 정밀판정: **Claude Sonnet** (고성능)

## 5. 프롬프트에 무엇을 주는가 — 룰 텍스트 + 실제 예시

각 룰을 판정할 때 모델에게 두 가지를 함께 준다:

1. **룰 텍스트 자체** (위 2절 표의 "룰" 정의 원문 — 이게 기준이 된다)
2. **실제 위반 예시 + 실제 예외(비위반) 예시** — 과거에 사람이 라벨링한 데이터셋에서
   가져온 진짜 사례. 애매한 경계 케이스를 판단할 때 참고 자료로 쓰인다.

둘 중 하나만 줬을 때보다 **둘을 같이 줬을 때가 확실히 더 좋았다** — 특히 예시만 주고
룰 텍스트를 빼면(모델이 정의 없이 패턴만 보고 유추해야 하는 상황) 위반을 거의 하나도
못 찾아냈다(실험에서 recall 0%). 룰의 공식 정의가 있어야 예시가 "이런 식으로 적용하면
된다"는 참고 자료로 제대로 작동한다는 뜻이다.

## 6. 위계(어느 범위의 문제인지) 판정과 승격

검토 단위(청크)는 "문단" 아니면 "문서 전체" 2종류뿐이지만, 실제로 보고되는 결과의
범위 표시는 **문서 / 논리단위 / 문단 / 문장**, 4단계 중 하나로 나온다. 이게 가능한
이유는 **승격(promotion)** 이라는 메커니즘 때문이다.

- 모델이 문단 하나를 검토하다가, "이 문제는 사실 이 문단 하나만의 문제가 아니라, 이
  문단이 속한 상위 논리단위(또는 문서 전체) 차원의 문제"라고 스스로 판단하면, 그
  판단을 그대로 인정해서 **더 넓은 범위(문단 → 논리단위, 또는 그 이상)로 승격**해서
  보고한다.
- 예: 문단 단위로 검토하다가 발견한 용어 불일치가, 사실 그 문단이 속한 큰 절 전체에
  걸쳐 반복되는 문제라면 → `Logical Unit`(논리단위) 레벨로 승격 보고.

**지금은 승격만 가능하고, 반대 방향(더 좁게 보고하는 것 — 예: 문단 청크를 보다가
"사실 이 중 문장 하나만의 문제"라고 좁히는 것)은 아직 데모2에는 들어가 있지 않다.**
(별도 개발 브랜치에서 검증 중 — 필요하면 이후 버전에 반영 예정)

## 8. 결과물 형식 (예시 1건)

에이전트가 위반을 발견하면 아래 형식으로 출력한다(실제 데모2 결과에서 가져온 예시 —
**정답 데이터셋(golden)에도 같은 위치·같은 룰로 등록된, 사람이 확인해도 실제로 맞는
지적**이다. 다만 정답 데이터셋은 이 문제를 "문장" 단위로 더 좁게 분류해뒀는데
에이전트는 "문단" 단위로 보고해서, 범위 판정까지 완전히 일치하진 않았다 — 6절에서
설명하는 "더 좁게 보고하는 기능"이 데모2에 없어서 생기는 차이의 실제 사례이기도 하다):

```json
{
  "rule_id": "AE-03",
  "level": "Paragraph",
  "location": "4. 상품 컨디션 등급 기준",
  "description": "'객관적 기준'이라는 표현이 무엇을 의미하는지 구체적으로 정의되어 있지 않음",
  "original_text": "경계 사례(예: A와 B 사이)의 경우 보수적으로 판단하여 객관적 기준에 따라 적절히 낮은 등급을 부여한다.",
  "rationale": "등급 표의 각 등급 기준 자체도 이미 정성적인데, 경계 사례에서 참조해야 할 '객관적 기준'이 별도로 명시되지 않아 담당자마다 판단이 달라질 수 있다.",
  "fix_direction": "예를 들어 '스크래치 개수, 가죽 변색 면적, 구성품 포함 여부 등 체크리스트 기준 3가지 중 2가지 이상 하위 등급에 해당하면 낮은 등급을 부여한다'와 같이 구체적인 판단 기준을 명시할 것을 제안."
}
```

- `related_location`: GA/LG/LF(관계형) 카테고리에서만 채워짐 — 충돌하는 "상대방" 위치.
- 단순히 "위반이다"만 말하지 않고, **왜 위반인지(rationale)**와 **어떻게 고치면
  되는지(fix_direction)**까지 항상 같이 준다.

## 9. 품질을 어떻게 검증하는가

검토 에이전트가 낸 결과가 실제로 맞는지는, 사람이 직접 라벨링해둔 "정답 데이터셋"과
자동으로 대조하는 **평가 에이전트**가 별도로 확인한다.

- 사람이 미리 찾아둔 진짜 문제 목록(golden 데이터셋)과, 검토 에이전트가 찾은 목록을
  자동으로 짝지어서 **recall**(진짜 문제 중 몇 %를 찾았는지)과 **precision**(찾았다고
  한 것 중 몇 %가 진짜인지)을 계산한다.
- 최근 이 짝짓기 로직을 사람 판단(LLM)이 아니라 결정론적 규칙(같은 룰 + 같은 위치를
  가리키면 매칭)으로 바꿔서, **같은 입력이면 항상 같은 채점 결과가 나오도록** 신뢰도를
  높였다.

## 10. 알려진 한계 (참고용)

- 지금까지의 실험은 표본 문서 수·정답 라벨 수가 많지 않아서, 수치(%)를 절대값으로
  인용하기보다 "이 구조가 이런 이유로 낫다"는 방향성 근거로 쓰는 게 안전하다.
- 일부 golden 정답 항목(예: 특정 관계형 위반)은 지금 구조로 아직 한 번도 잡아낸 적이
  없다 — 계속 개선 중인 부분이다.
- 6절에서 설명한 "승격"은 있지만 "더 좁게 보고하는 것"은 아직 데모2에 없다.
