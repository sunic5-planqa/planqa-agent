# 팀 룰 실시간 추가 (자연어 → 룰 + 퓨샷 자동 합성)

- Status: Draft
- Date: 2026-08-19

## Context

지금 review-agent는 고정 룰북(`data/rulebook/rulebook_v1.0.md`, 40개 룰)과 골든 데이터셋
실사례에서 손으로 큐레이션한 퓨샷(`fewshot_bank.py`, 룰당 위반 예시 2개 + 예외 예시 1개)에
의존한다. 팀마다 자기 도메인에 맞는 룰을 추가로 쓰고 싶을 때, 지금처럼 사람이 매번 카테고리/
티어/퓨샷을 손으로 큐레이션하는 방식은 스케일이 안 된다.

원하는 것: 사람이 자연어로 룰을 던지면 시스템이 (a) 프롬프트로 변환하고, (b) 룰별 퓨샷(위반
예시 2개 + 예외 예시 1개)을 자동 생성하고, (c) 실시간으로 리뷰에 반영한다.

제약과 이미 확인한 어려움:

- 기존 파이프라인은 `category`(AE/GA/LF/…) × `tier`(DOCUMENT/LOGICAL_UNIT/PARAGRAPH/
  SENTENCE) 2축 라우팅(`tiers.py`의 `TIER_CATEGORIES`)에 강하게 결합돼 있다. `RuleDef`
  (`planqa_schemas/rulebook.py`)는 `rule_id`/`category`/`category_label`/`text`/
  `fixed_level`/`exception_text` 필드를 갖는다.
- 새로 들어온 자연어 룰을 이 그리드의 어느 칸(카테고리+티어)에 넣을지 자동으로 판정하는 게
  어렵다 — "팀별 에이전트 분류가 어려울 수 있음"의 실체는 이 라우팅 판정 문제다.
- 팀 룰에는 골든 데이터셋 같은 실제 위반/예외 사례가 없다. 퓨샷을 LLM이 즉석에서 합성해야
  하고, 합성 퓨샷은 골든셋 퓨샷만큼 신뢰할 수 없다.
- "실시간 적용"과 "결과 신뢰성" 사이에 사람이 확인할 지점이 필요한지가 쟁점이다.
- 실행 순서 문제: 팀룰을 저장해두는 경우, 매 리뷰마다 팀룰과 기본룰을 따로 두 번 돌릴지,
  하나로 합쳐서 한 번에 돌릴지 정해야 한다.
- 프롬프트 캐싱 문제: 팀 룰북(퓨샷 포함)을 한 번 업로드해두면 이후 계속 캐싱된 채로 남는지
  확인이 필요하다.

## Options

1. **완전 자동 실시간 적용** — LLM이 룰 텍스트만 보고 카테고리/티어/퓨샷을 전부 생성해 검증
   없이 즉시 `RuleBook`에 병합한다. 가장 빠르지만, 분류 오류나 저품질 합성 퓨샷이 검증 없이
   그대로 리뷰 결과에 반영되는 리스크를 감수해야 한다.
2. **사람 승인 게이트가 있는 반자동 저작 파이프라인** — 별도 "룰 저작 에이전트"가 카테고리/
   티어/합성 퓨샷 초안을 만들고, 사람이 확인·수정한 뒤에만 `RuleBook`에 병합한다. 팀룰과
   기본룰은 병합된 하나의 `RuleBook`으로 기존 `review_document`에 그대로 흘러간다(팀룰
   전용 별도 파이프라인을 새로 만들지 않는다).
3. **팀별 완전 분리 파이프라인** — 팀마다 별도 `RuleBook` + 별도 `review_document` 호출을
   순차 실행한다. 팀룰 오류가 기본룰 리뷰에 전혀 영향을 주지 않는 격리 장점이 있지만,
   `global_context` 재추출 등 비용이 두 배가 되고 `tiers.py`의 통합 라우팅 이점을 버리게
   된다.

## Decision

Option 2를 채택한다 (Draft 단계 — 실제 구현 착수 시 재확인).

- 신규 "룰 저작 에이전트"(가칭 `rule_author`)를 review-agent 옆에 별도 모듈로 추가한다.
  - 입력: 자연어 룰 텍스트 (+ 선택적으로 해당 팀 문서 일부 — 있으면 합성이 아니라 실제
    문서에서 위반/예외 사례를 뽑아 퓨샷 품질을 golden set 방식에 가깝게 끌어올린다).
  - 출력: `RuleDef` 초안(카테고리·티어 추정 포함) + `FewShotExample` 2개(위반) +
    `FewShotException` 1개(예외).
  - 사람 확인을 거쳐야 `team_rulebook/`(팀별 네임스페이스, 예: `team_id` 프리픽스가 붙은
    `rule_id`) 아래 정적 파일로 영구 저장된다. 이후 실제 리뷰에서 확정된 위반 사례가
    쌓이면, 초기 합성 퓨샷을 실사례로 교체하는 피드백 루프는 후속 과제로 남긴다.
- 실행 시점에는 팀룰이 저장돼 있으면 팀 `RuleBook`과 기본 `RuleBook`을 병합해서
  `review_document` 한 번으로 실행한다. `tiers.py` 라우팅을 그대로 재사용하고,
  `RuleDef`에 `team_id`(optional) 필드를 추가해 결과 리포트에서 룰 출처를 구분한다.
- 자동 분류(카테고리/티어) 신뢰도가 낮게 나오면 안전한 기본값(DOCUMENT tier, 전체
  카테고리)으로 폴백해 놓치는 것보다 과호출되는 쪽으로 fail-safe 한다.
- 프롬프트 캐싱: 병합된 `RuleBook`의 퓨샷 블록을 시스템 프롬프트 prefix 고정 위치에 두고
  그 뒤에 `cache_control: {type: "ephemeral"}` 브레이크포인트를 건다. 이는 "한 번 올리면
  영구 캐싱"이 아니라 TTL(기본 5분, extended cache beta 사용 시 1시간) 내 연속 호출에서만
  캐시 재사용 비용 절감이 일어나는 구조다 — 같은 리뷰 런 안에서 티어별로 연속 호출되는
  현재 파이프라인 특성상, 첫 호출 이후 런이 끝날 때까지는 사실상 계속 캐시가 유지된다.

## Consequences

- 장점: 기존 `RuleDef`/`tiers.py`/`pipeline.py`를 그대로 재사용해 신규 인프라를 최소화한다.
  팀룰과 기본룰의 실행 경로가 하나로 통일돼 유지보수가 단순해진다.
- 단점: 사람 확인 게이트가 있는 한 "완전 실시간" 목표와는 상충한다 — 1차 버전은 "승인 후
  반영"되는 준실시간으로 스코프를 낮춰야 한다.
- 리스크: 자동 카테고리/티어 분류 정확도가 낮으면 팀룰이 엉뚱한 스크리닝 단계에서 누락되거나
  과도하게 호출될 수 있다. 합성 퓨샷의 품질이 golden set 퓨샷보다 낮아 팀룰 쪽 정밀도가
  기본룰보다 떨어질 가능성이 있다 — 결과 리포트에서 팀룰 이슈를 구분 표시해 신뢰도 차이를
  드러낼 필요가 있다.
- 후속 작업:
  1. `rule_author` 모듈 스펙 확정 (입출력 스키마, 분류 프롬프트, 합성 퓨샷 프롬프트)
  2. `team_id` 필드를 `RuleDef`/`RuleBook`에 추가하는 스키마 마이그레이션
  3. 합성 퓨샷을 실사례로 승격시키는 피드백 루프 설계
  4. 사람 확인 UI/CLI 플로우 정의
